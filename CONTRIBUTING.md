# Contributing

Thank you for considering a contribution. ManipulatorCore values mathematical correctness, explicit
conventions and tests over feature count.

## Workflow

1. Open an issue describing the change (bug, algorithm, documentation) before larger work.
2. Create a branch, keep commits focused, and use conventional commit messages
   (`feat(planning): ...`, `fix(collision): ...`, `docs: ...`, `test: ...`).
3. Make sure the full local check passes (below) and open a pull request.

## Local checks

```bash
cmake --preset debug && cmake --build --preset debug && ctest --preset debug
cmake --preset release && cmake --build --preset release && ctest --test-dir build/release
git ls-files '*.hpp' '*.cpp' | xargs clang-format --dry-run --Werror
cmake --preset asan-ubsan && cmake --build --preset asan-ubsan && ctest --test-dir build/asan-ubsan
pip install -e ".[dev]" && ruff check python scripts && ruff format --check python scripts && pytest
python scripts/docs/generate_status_matrix.py --check
```

## Rules for code

* Follow [docs/mathematics/conventions.md](docs/mathematics/conventions.md) exactly (frames,
  `[omega; v]` ordering, Jacobian/pose-error pairing, units). If a new convention is needed, document
  it there in the same change.
* Invalid input throws `mc::InvalidArgument`; expected algorithmic failures are reported in result
  structs. Never return NaN or infinity for valid input; library code never prints.
* Solve linear systems with factorizations; use the SVD (with an explicit tolerance) for rank and
  pseudoinverses. Never form an inverse to solve `A x = b`.
* Randomized algorithms take an explicit seed and use `mc::Random`.
* No raw owning pointers; prefer value types, `const`, and `std::shared_ptr<const T>` for shared
  immutable data.
* Warnings are errors in CI (`MC_WARNINGS_AS_ERRORS=ON`).

## Rules for tests

* Every algorithm needs tests that check it against an independent reference: closed-form results,
  finite differences, a second algorithm, conservation laws or brute force.
* Use deterministic seeds; avoid golden values that depend on standard-library distributions.
* Put tests in `tests/unit`, `tests/numerical` (edge cases, conditioning) or `tests/integration`
  (multi-module pipelines), and register new algorithms in `configs/algorithms.yaml`.

## Figures and benchmarks

* Figures are generated by `scripts/render` from data computed by `mc_demos`; never commit hand-made
  or raw frame assets. Keep each animation well under 5 MB.
* Only commit benchmark numbers produced by `scripts/benchmark/run_benchmarks.py` on a Release build.
